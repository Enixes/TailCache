Same write rate, different winner

At 4 KiB and the same 5% write rate, Caffeine led when writes targeted a small set of keys. Chronicle led when updates reached across the cache. Compare operation time, scheduled response, and garbage collection.

Where writes land

The cache always held 32,768 entries. Reads could access any key. Only the eligible write set changed between the two groups.

4 KiB values, 5% writes, 50,000 intended arrivals/s, and zero added application data. Evidence and replication

What changes at heavier loads?

The 50,000-arrival baseline and the 100,000-arrival arm both delivered about 2,500 writes/s. The 10% and 20% arms increased writes while keeping arrivals at 50,000/s.

4 KiB values, zero added application data, two paired seeds per setting, and 30-second windows on Pop!_OS. Archived follow-up evidence

Value size changes the operation-time winner

A hit on Caffeine returns the stored array. Ordinary Chronicle reads allocate a Java array and copy in the value. Update timing includes allocating and filling a fresh array on both backends.
