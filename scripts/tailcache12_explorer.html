Understand the terms: memory, request timing and percentiles

We give both caches the same application data and allocation demand, then measure how memory pressure changes their speed. These definitions describe this benchmark; scheduled arrivals are simulated inside it, without a network.

Heap
Memory managed by Java’s garbage collector. Its maximum is fixed at 512 MiB in these runs.
Off-heap
Memory outside Java’s managed heap, still using the machine’s RAM. Chronicle keeps its cache payloads here; ordinary reads can still create heap objects.
Ballast / common application ballast
Extra application data deliberately kept alive, representing the rest of an application. Labels count array payload, excluding object/container overhead. Zero means no added ballast, not zero application memory. Both caches receive the same amount.
RSS / process residency
RAM currently resident for the process, sampled about once per second in the fresh follow-up. It includes more than Java’s heap. A lower post-GC heap percentage does not establish lower RSS or an equal total-memory budget.
Churn / allocation demand
Temporary objects repeatedly created and discarded, giving the garbage collector ongoing work. Both backends receive 32 MiB/s of offered background allocation.
GC pause / post-GC occupancy
A GC pause stops application execution for garbage collection. Post-GC occupancy is the fraction of the heap still used after collection. Off-heap storage reduces retained heap; it does not eliminate GC.
Saturated workload
One worker starts the next operation as soon as the previous one finishes, working as fast as possible. It cannot generate new requests while paused.
Scheduled workload
Requests have intended arrival times at 50,000/s, one every 20 µs. The schedule continues through pauses; overdue requests wait, and are processed when the worker catches up.
Service time
Actual start to completion of one operation, ending before recording/bookkeeping and next-operation pacing. A delay between operations can affect gaps and later response without entering either service duration. Saturated and scheduled service belong to their respective workloads.
Response time / waiting time
Response runs from intended arrival to completion, including waiting before execution starts. Response time = waiting time + service time. Scheduled response shows the effect of queued demand during pauses.
Gap
Time between successive operation completions. It includes work and intervening delays; it is a separate diagnostic, not intended-arrival response time.
Percentile / tail latency
p99, p99.9, p99.99 and p99.999 describe successively slower parts of the distribution. Roughly 1 in 100, 1,000, 10,000 and 100,000 observations respectively are slower. Equal-value histogram bins can change the exact fraction.
Tail curve / stall probability
A tail curve shows the fraction of operations slower than each latency threshold. A stall probability is that fraction at a specific threshold, such as greater than 1 ms. It counts operations, not independent pause episodes.
Histogram resolution bounds
The recorder groups nearby times into buckets. If a threshold cuts through a bucket, the table shows the definite–possible number of exceedances. These bounds describe timing resolution, not statistical uncertainty.
Nominal upper-tail observations
Operation count multiplied by the fraction beyond a percentile. At p99.999, 400,000 responses give only 4 nominal tail observations. These counts are not independent pause episodes or a confidence interval.
Throughput / payload
Throughput is completed operations per second. Payload is the value stored for each key: 256 bytes or 4 KiB here. MiB and KiB are binary memory units.
Fork / measured window / runtime
A fork is a separate Java process repeating a measurement. The window is its 8 or 30 seconds of measurement. Runtime groups identify the compiled builds; their results remain separate.
Ordinary get / getUsing
Ordinary get returns a value; Chronicle materializes an array while Caffeine can return its existing one. getUsing reuses a caller buffer with borrowed contents. That different ownership contract has its own paired controls.
Paired ratio / crossover
The ratio is Chronicle latency divided by Caffeine latency for a matched pair. Below 1 favors Chronicle. A crossover is a change in ordering between measured pressure points; connecting lines do not locate an exact threshold.

A fast operation can still give a slow response

A request is due at 10:00:00.000, starts at 10:00:00.020 and takes 5 µs to execute.

Waiting: 20 ms · Service: 5 µs · Response: 20.005 ms.

At 50,000 requests/s, an illustrative 20 ms pause leaves about 1,000 intended arrivals waiting. A pause inside an operation can enter its service measurement; a pause between operations may enter no service duration. Scheduled response can show many delayed requests. Saturated and scheduled workloads are different runs; compare scheduled service and response to inspect boundaries within the same forks.

    Read the result, keep the context

    A crossover means the same endpoint changes ordering between observed pressure points. An advantage already present at zero ballast is not a newly observed crossover. A mixed pair set does not become a consistent result by taking its median.

    • Ordinary get is the primary ownership contract. getUsing borrows a read buffer and always uses its own paired Caffeine controls.
    • Service measures operation completion minus actual start. Response measures completion minus intended arrival, including queue debt. Gap is time between completions.
    • Both payloads use a 512 MiB G1 heap, 32,768 resident entries and 32 MiB/s offered background allocation. Scheduled load is 50,000 requests/s.
    • Builds, durations and read contracts remain distinct. The graph never joins them into one continuous experiment.

    Evidence and uncertainty

    All 132 workload forks completed. Warnings remain attached. At p99.99, an 8 s response window has 40 nominal observations in the upper 0.01%; a 30 s window has 150. At p99.999, the upper 0.001% has only 4 and 15 nominal observations respectively. This requested extension is exploratory and can be sensitive to a few events. Queued observations from one pause are correlated. More operation samples are not more independent forks.

    The original 8 s low-pressure response baseline is retained alongside the later 30 s batch. Pressure is common application ballast; heap occupancy is an observed backend-specific outcome.
