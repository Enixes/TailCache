# TailCache 07 — researcher review after implementation

## Verdict

The harness now supports a **diagnostic** warm persisted run with an explicit storage root, pre-timed page touches, raw SampleTime histograms, and separate process/JIT diagnostics. The 2026-10-04 pilot does **not** support a backend tail-latency ranking or a GC-pressure crossover claim. The 08 baseline must pass fresh gates; 07 numbers remain excluded.

## Construct and measurement validity

1. **Profiler contamination — repaired.** The original `tailCache07Pilot` attached Linux process and JMH compiler profilers to the sampled-latency fork. Internal profilers act around JMH iterations and can alter state between iterations. `tailCache07Pilot` now has no added profiler; `tailCache07PilotDiagnostics` uses separate forks and run IDs. A one-condition check found no OS sidecar or compiler secondary metric in the unprofiled directory, and both in the diagnostic directory. JMH's percentile entries remain ordinary SampleTime secondary metrics.
2. **Raw-result overwrite — repaired.** The original task could reuse a directory while old per-fork CSVs remained. Both tasks now reject a nonempty run directory. A deliberate rerun of the same ID failed before launching JMH, preserving the first raw result.
3. **Dead-code elimination — sufficiently controlled for this path.** Reads feed JMH `Blackhole`; puts mutate a map shared by later accesses. The reverse-order pilot observed 1,888 of 2,048 entries holding replacement values at teardown in every mixed fork, versus zero in floor forks. This proves that at least warmup/trial writes executed, not that each timed iteration had exactly 5% writes. The floor is a lower bound and must never be subtracted from a percentile.
4. **Persisted page state — unproven.** Trial setup reads every populated Chronicle entry and loads a second read-only mapping. Each iteration touches mapped pages without constructing returned `byte[]` values. `MappedByteBuffer.load()` requests residency but is not a pin; later eviction is possible. The Linux counters cover the whole JVM and the JMH profiler envelope, including setup. The pilot recorded major faults and process reads in some persisted conditions, so a cache-specific fault attribution and a warm-state qualification are still missing. Oracle documents that `load()` loads mapped content into physical memory but the mapping remains subject to OS behavior: [JDK 21 MappedByteBuffer](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/nio/MappedByteBuffer.html).
5. **Setup writeback versus steady-state writes — unresolved.** The 95/5 workload continues to dirty persisted pages during timed operation, so process `write_bytes` alone cannot disqualify a warm mixed workload. The post-fix short validation showed a 26,390,528-byte write burst with no major faults or process reads. The harness does not prove that setup writes had drained before timed operation. A separate `FileChannel.force` is not a reliable substitute for forcing another mapping's modifications; the JDK documents this limitation: [JDK 21 FileChannel](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/nio/channels/FileChannel.html). Future work must explicitly distinguish setup writeback from normal mixed-workload writeback, ideally with a Chronicle-supported sync or map-specific observation.
6. **Warmup/JIT — failed gate.** Eight one-second warmups did not yield stable iteration trajectories. A separate fixed-heap diagnostic still recorded whole-JVM compiler time during measurement (108 ms Caffeine, 201 ms persisted Chronicle across five iterations). This cannot identify which method was compiled, but it prevents a claim that measurement was free of compilation disturbance.
7. **Environment and variance — failed gate.** The host had 7.6 GiB RAM, roughly 8.6 GiB swap in use during the pilot, a `powersave` governor, and marked memory/I/O pressure. Caffeine 256 B p99 moved from 1,130 to 2,460 ns between order-reversed runs. Persisted 256 B recorded 1,033 process major faults and 78,180,352 process read bytes in the second run. These are invalid conditions for precise tail comparisons.

## Claim limits carried into 08

- The workload is closed-loop, one-JVM, all-hit, mixed read/existing-key-put traffic. A percentile is for the mix, not read-only latency or production response time.
- The per-key replacement-value bank leaves a substantial Chronicle shadow payload set on the Java heap. This baseline can study access cost, but cannot answer whether off-heap storage reduces live heap or GC tails.
- The 2,048-resident/4,096-configured setting sits at Caffeine's documented frequency-sketch activation boundary discussed in the project plan. It is a frozen **baseline setting**, not evidence of equivalent Caffeine/Chronicle capacity semantics or a reportable occupancy protocol.
- JMH SampleTime randomly samples invocations. A rare pause can be absent from the sampled tail even when JVM pause logs show it occurred. GC-driven p99/p99.9 claims need the separate pause-sensitive method listed in the plan.
- The reopen/first-touch task is separate from warm operation samples. Its OS page cache is uncontrolled; it measures a descriptive close/reopen sequence, not a guaranteed cold-storage access.

## Verification performed after the repair

`./gradlew --offline test tailCache07Pilot` and `tailCache07PilotDiagnostics` passed for one 256 B Caffeine condition with one short fork each. The duplicate run-ID check failed intentionally with the expected preservation error. No new 07 latency was promoted to a research result.
