# TailCache 09 — sizing sensitivity and researcher review

## Design and implementation

TailCache 09 is an isolated Chronicle Map study. It leaves the primary adapter untouched. A fresh map with `entries=256`, `maxBloatFactor=1.0`, and segment tiering enabled is built for each actual value length (256 or 4,096 bytes) and sizing rule: `HALF`, `MATCH`, `DOUBLE`, or `CONSTANT`. The first three use Chronicle's `averageValue(byte[])` with a sample array of half, equal, or double the actual payload length. `CONSTANT` uses `constantValueSizeBySample(byte[])` at the actual length, matching the primary adapter's fixed-size declaration. These are **nominal sample payload lengths**; Chronicle's serialized lengths can include array metadata. The official [Chronicle Map builder source](https://github.com/OpenHFT/Chronicle-Map/blob/ea/src/main/java/net/openhft/chronicle/map/ChronicleMapBuilder.java) and [tutorial](https://github.com/OpenHFT/Chronicle-Map/blob/ea/docs/CM_Tutorial.adoc) distinguish average and constant sizing.

`tailCache09Capacity` inserts unique deterministic keys until the first failure in fresh in-memory and persisted maps; it records accepted count, final size, failure class/message, censoring, and persisted file length. Capacity insertion is outside timed JMH. Separate `tailCache09Latency` and `tailCache09Throughput` tasks use one worker, an in-memory map prefilled to 192 existing keys, a pre-generated uniform 95/5 get/put trace, and observable read results and writes. The 192-key set is below the lowest in-memory failure boundary observed (300), so timing does not include exhaustion. `scripts/tailcache09_audit.py` joins and checks the three raw sources.

## Validation observations (2026-10-04)

All 16 capacity conditions produced a recorded `IllegalStateException` on extra-tier allocation before the 4,096-insert censor limit. For 256-byte actual values, in-memory successful inserts were 300 (`HALF`), 526 (`MATCH`), 818 (`DOUBLE`), and 512 (`CONSTANT`); persisted results were 306, 532, 818, and 512. For 4-KiB values, in-memory counts were 342, 688, 1,377, and 688; persisted counts were 342, 688, 1,382, and 688. This demonstrates that the sizing perturbation changed realized capacity. Persisted file size at failure increased with larger configured samples (for 4 KiB: roughly 1.59 MiB, 3.14 MiB, 6.08 MiB for half/match/double). Because segment tiering allows expansion, `entries=256` is a planning target rather than a hard insertion cap. The raw first-failure messages are retained; they identify extra-tier exhaustion, not a generic Java heap failure.

The initial 64-resident timing validation was too far from every capacity boundary. After review, the benchmark gained an explicit `residentEntries=192` JMH parameter and was rerun. All eight sizing conditions completed in both latency and throughput modes, and teardown found 192 entries updated in each fork. The joined summary remains `validation_only`: each condition had one one-second warmup, one one-second measurement and one fork on the already pressured host. The p99 and throughput figures are pipeline checks, not estimates of a sizing effect.

## Validity limits and next candidate

1. `averageValue` changes chunk layout and potentially segment allocation, so the capacity contrast is a response to Chronicle's complete sizing policy. The nominal half/match/double ratios are not measured serialized-byte ratios. `CONSTANT` and `MATCH` are different builder contracts even when their samples have the same nominal length.
2. Capacity is an insertion-to-first-failure count for sequential keys under this seed, segment tiering, and bloat limit. Hash distribution and configuration can move the boundary. The 16 rows are one fresh-map realization each, not a capacity distribution. File length is recorded for persisted maps; in-memory off-heap allocation was not independently measured.
3. Timed paths operate at 192 keys, below all observed boundaries. They measure serialization/get/put costs for the 95/5 mix, not performance at exhaustion or eviction. Reads feed JMH `Blackhole`, writes alter later reads, and teardown checks observable replacement values. This controls elimination but does not prove a production access pattern.
4. The first timing pass used a fixed estimate order; host drift could bias the comparison. The task now accepts `-Ptailcache09Estimates` and `-Ptailcache09Payloads` so a future candidate can repeat with reversed estimate order and independent forks. The current one-fork validation cannot quantify run-to-run variance or p99.9 uncertainty. JMH SampleTime observes selected invocations, so rare stalls may be missed.
5. Persisted capacity is a distinct checksum/storage stratum. Timed 09 results are in-memory only, avoiding page-fault contamination of this sizing question. Neither the persisted capacity counts nor the 09 timing checks repair TailCache 08's invalid persisted-warm baseline or answer its heap/GC crossover questions.

**Verdict:** The study design and measurement paths are implemented and the capacity perturbation is verified. Retain the 2026-10-04 timing results as validation only. Repeat under a quiet host with planned warmup, two or more forks, reversed estimate order, and independent capacity replicates before claiming a throughput or tail-latency effect.


## Final task closure

TailCache 09 is **closed as an implemented and validated diagnostic study**, not as a reportable latency-effect estimate. The capacity perturbation is real and retained raw evidence demonstrates that Chronicle sizing policy changes realized capacity. The timed one-fork results remain validation-only.

A longer reportable sizing campaign is deliberately not launched now. TailCache 10 remains NO-GO and the project scope says secondary sensitivity work must not displace the unresolved primary crossover harness. If sizing later becomes necessary to explain an RQ1/RQ2 crossover, rerun 09 with the stronger replication policy, reversed estimate order and independent capacity replicates. Until then, the current capacity result is the completed deliverable.
